### <a name="_qmphm5d6rvi3"></a>**Решение**

Переносим всех действующих лиц и системы из таблицы Use Cases. 
Действующие лица: Клиент, Оператор кол-центра, Менеджер фронт-офиса, Специалист бэк-офиса (Депозиты), 
Специалист бэк-офиса (Кредиты), IT-отдел. Системы: Сайт (PHP + React.js), 
Интернет-банк (ASP.NET MVC + MS SQL), Система кол-центра (Java Spring Boot + PostgreSQL), 
АБС (Delphi + Oracle PL/SQL), Сервис управления заявками (Java Spring Boot), SMS-шлюз (внешний).

Взаимодействия по Use Cases: UC1 и UC2 (Сайт) - Клиент взаимодействует с Сайтом, 
Сайт передаёт заявку в Сервис заявок. UC3 (Передача в КЦ) - Сайт передаёт заявку в 
Систему кол-центра. UC4 (Обработка заявки) - Оператор кол-центра связывается с Клиентом по телефону. 
UC5 и UC6 (ИБ) - Клиент работает в Интернет-банке, Интернет-банк передаёт заявку в Сервис заявок, 
подтверждение проходит через SMS-шлюз. UC7 (Обработка заявки) - 
Сервис заявок отправляет заявку в очередь (Kafka), оттуда она асинхронно передаётся в АБС. 
UC8 (Подтверждение) - Специалист бэк-офиса подтверждает депозит в АБС. UC9 (Уведомление) - 
АБС отправляет команду в SMS-шлюз, SMS-шлюз уведомляет Клиента. 
UC10 (Идентификация) - Новый клиент приходит в отделение к Менеджеру фронт-офиса.

Архитектурное допущение: вводим Сервис управления заявками как буфер между онлайн-каналами и АБС, 
так как АБС перегружена и масштабируется только вертикально.
Заявки передаются асинхронно через очередь (Kafka). 
SMS-функционал реализуется силами команды банка через существующий SMS-шлюз.

![Диаграмма контекста в модели С4](https://github.com/rume73/architecture-standart/blob/standart/diagrams/context/Standart_Context_3.png?raw=true)

1. **Защита АБС от перегрузки (требования P3, +R1, +R4).** АБС масштабируется только вертикально и уже перегружена. Поэтому Интернет-банк не обращается к АБС напрямую. Вместо этого заявки поступают в новый Сервис заявок, который отправляет их в АБС асинхронно через очередь Kafka. Это позволяет сгладить пиковые нагрузки.

2. **Обеспечение производительности (требование P1).** Для достижения времени отклика в миллисекунды вводим слой кеширования на базе Redis. В кеше хранятся справочные данные и ставки, которые часто запрашиваются пользователями. Это разгружает как Интернет-банк, так и АБС.

3. **Достижение высокой доступности (требования R1, R2, R3).** Все новые сервисы проектируются с поддержкой горизонтального масштабирования (требование P2). Добавляем балансировщик нагрузки, реплики приложений. Для обеспечения отказоустойчивости используем резервный ЦОД с автоматическим переключением.

4. **Использование существующих технологий (требование +R3).** Для новых компонентов выбираем Java Spring Boot, так как в команде АБС уже есть экспертиза Java. База данных MS SQL используется для новых сервисов. REST API обеспечивает совместимость с React.js на фронтенде.

5. **Безопасность передачи данных (требование +R2).** Все интеграции между системами обеспечить шифрованием трафика и защиту персональных данных.

6. **Документирование для будущего развития (требование +R5).** Архитектура документируется в формате ADR, что позволяет последовательно расширять систему на следующих этапах.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
1. Не создавать отдельный Сервис управления заявками, а интегрировать Интернет-банк напрямую с АБС через синхронный API.

2. Реализовать ставки по депозитам в отдельном микросервисе с нуля, а не в АБС.

3. Переписать весь Интернет-банк на микросервисную архитектуру, а не только функционал по депозитам.

4. Использовать Oracle для нового сервиса заявок вместо MS SQL.

**Недостатки, ограничения, риски**

1. Сервис управления заявками является новым компонентом, который требует разработки с нуля и интеграции с существующими системами - это увеличивает сроки MVP и требует дополнительных ресурсов команды.

2. На этапе MVP обработка заявок бэк-офисом остаётся ручной, поэтому полного сокращения операционных издержек не происходит - это временное ограничение до следующего этапа автоматизации.

3. Использование Kafka требует доработки Интернет-банка, так как текущая версия платформы несовместима с Kafka - на MVP заявки передаются через REST в Сервис заявок.

4. АБС остаётся монолитной системой с вертикальным масштабированием, что создаёт риск перегрузки при росте числа онлайн-заявок, несмотря на использование асинхронной очереди.

5. В банке нет готовой инфраструктуры для новых технологий (Redis, Kafka) - потребуется время на развёртывание, настройку и обучение команды.

6. Отсутствие документации по новым компонентам может затруднить дальнейшее развитие системы - необходимо заложить время на документацию в спринте.

7. Высокая нагрузка на команду разработки, так как одновременно ведётся работа над новым сервисом, интеграциями и доработкой существующих систем.
