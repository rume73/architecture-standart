| **№** | **Требование** |
| :-: | :-- |

| R1 | Система должна быть доступна для сотрудников кол-центра в рабочее время |

| R3 | Передача ставок партнёрскому кол-центру должна иметь контроль успешности передачи |
| P | **Производительность (Performance)** |
| P1 | Получение ставок оператором кол-центра должно занимать минимальное время |

| +R4 | Используются существующие технологии банка (.NET, Java, MS SQL, Oracle) |

### <a name="_qmphm5d6rvi3"></a>**Решение**

Переносим действующих лиц и системы из Use Cases.

**Действующие лица:**

- Клиент
- Оператор банковского кол-центра
- Оператор партнёрского кол-центра
- Специалист бэк-офиса депозитов
- IT-команда банка

**Системы:**

- XLS-файлы ставок
- Новый Сервис управления ставками
- База ставок (MS SQL)
- Система кол-центра (Java Spring Boot + PostgreSQL)
- Партнёрский кол-центр (внешняя система)
- Файловое хранилище

---

### **Взаимодействия по Use Cases**

**UC1, UC2, UC3 (Подготовка и хранение ставок)**

Сейчас ставки хранятся в XLS-файлах. Специалисты бэк-офиса продолжают использовать текущий процесс подготовки ставок.

Добавляется Сервис управления ставками, который загружает данные из XLS-файлов и сохраняет их в собственной базе данных.

---

**UC4, UC5 (Работа банковского кол-центра)**

Система кол-центра получает актуальные ставки через REST API от Сервиса управления ставками.

Оператор кол-центра использует полученную информацию для консультации клиентов по депозитам.

---

**UC6, UC7 (Передача ставок партнёрскому кол-центру)**

Сервис управления ставками формирует файл с актуальными депозитными ставками.

Файл передаётся партнёрскому кол-центру через файловый обмен.

Так как партнёрская система не поддерживает API-интеграцию, используется обмен файлами.

---

**UC8 (Обновление ставок)**

После изменения ставок специалист бэк-офиса обновляет XLS-файл.

После загрузки новые значения становятся доступны банковскому и партнёрскому кол-центрам.

---

## **Архитектурное решение**

Вводится новый компонент — **Сервис управления ставками**.

Он становится единым источником актуальной информации по депозитным ставкам для всех каналов обслуживания.

На MVP текущий процесс формирования ставок через XLS-файлы сохраняется.

XLS используется только как источник загрузки данных.

Сервис предоставляет:

- REST API для банковского кол-центра;
- генерацию файлов для партнёрского кол-центра;
- хранение истории изменений ставок.

---

### **Причины выбора решения**

### **1. Централизация ставок (UC3, +R1)**

Сейчас ставки находятся только в XLS-файлах.

Использование отдельного сервиса позволяет избежать ситуации, когда разные подразделения используют разные версии ставок.

---

### **2. Быстрое получение информации кол-центром (UC4, P1)**

Оператор получает актуальные ставки через API без необходимости ручного поиска информации.

---

### **3. Поддержка партнёрского кол-центра (UC6, UC7, +R2, +R3)**

Так как партнёрская система не поддерживает API, используется файловый обмен.

---

### **4. Использование существующих технологий (+R4)**

Для нового сервиса используется Java Spring Boot.

В качестве базы данных используется MS SQL, так как технология уже применяется в банке.

---

### **5. Возможность дальнейшего развития (+R5)**

В будущем XLS-файлы могут быть заменены полноценным модулем управления ставками внутри банковской системы.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

### **1. Передавать XLS-файлы напрямую в кол-центр**

**Недостатки:**

- отсутствует единый источник ставок;
- высокий риск использования устаревших данных;
- нет контроля версий.

---

### **2. Хранить ставки непосредственно в системе кол-центра**

**Недостатки:**

- появляется дублирование данных;
- необходимо обновлять несколько систем;
- усложняется сопровождение.

---

### **3. Реализовать хранение ставок сразу в АБС**

**Недостатки:**

- требуется изменение критичной банковской системы;
- увеличиваются сроки MVP;
- повышается риск для основной системы банка.

---

### **4. Создать API для партнёрского кол-центра**

**Недостатки:**

- невозможно реализовать из-за ограничений внешней системы;
- требуется изменение инфраструктуры партнёра.

---

# **Недостатки, ограничения, риски**

1. XLS-файлы остаются временным источником ставок.

2. Новый сервис требует разработки и дальнейшей поддержки.

3. Возможны ошибки при загрузке данных из XLS.

4. Необходимо реализовать контроль версий ставок.

5. Передача файлов партнёру зависит от внешнего процесса обмена.

6. При увеличении количества депозитных продуктов потребуется развитие сервиса.

7. В будущем потребуется перенос управления ставками из XLS в автоматизированную систему банка.
